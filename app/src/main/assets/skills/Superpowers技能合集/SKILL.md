# Superpowers 技能合集（14 个内置技能）

收录 obra/superpowers 的核心工程方法论，覆盖「想清楚 → 定计划 → 写代码 → 验证 → 收尾」的全流程。AI 在遇到开发任务时应主动匹配，避免用平庸常识应付。

> 重要：本合集面向灵犀环境做了适配——原版依赖的"子代理/subagent、git worktree、跨会话执行"等机制，在灵犀环境统一改为「AI 在单会话内分步自主完成 + 通过 use_skill 加载对应方法论」。

---

## 技能分类

### 🔀 过程与设计 (3 个技能)

#### brainstorming
**描述**: 在动手实现任何创意性工作前必须使用。通过提问澄清用户意图、需求与设计，把想法变成完整设计/规格，避免凭空实现。
**使用场景**: 用户提出新功能、想构建某组件、要加功能时，**先问清楚再做**，别急着写代码。
**核心要点**: 给实现前设"硬门槛"——必须先向用户说明打算做什么并获确认，才能写代码。按任务规模分三档：可行性试探(Spike)/小型改动(有界)/架构级(需写设计)，先分类再决定要多少流程，但"先经用户同意再动手"这一门槛永不取消。

#### writing-plans
**描述**: 在需要多步骤的大任务、有需求却还没写代码时，先把实现计划写清楚，再分小步执行。
**使用场景**: 拿到需求/规格要落地多步功能时，先写详细实施计划。
**核心要点**: 计划要"bite-sized"小步拆解，每步能独立测试、有独立交付物；标注要改哪些文件、怎么测、涉及哪些文档；遵循 DRY / YAGNI / TDD / 频繁提交。写计划前先大声宣告"正在用 writing-plans 创建实施计划"。

#### executing-plans
**描述**: 有了书面实施计划后，逐任务执行、关键处设评审检查点，结束时如实汇报。
**使用场景**: 拿到计划要落地执行时。
**核心要点**: 加载计划→批判性复核→逐任务执行。每个任务完成都要验证是否达标，遇到计划与实际不符要停下说明，不要带病往下冲；全部完成后汇总结果、说明是否达成、遗留事项。

### 🔧 实现与调试 (4 个技能)

#### test-driven-development
**描述**: 实现任何功能或修任何 bug 前，先写会失败的测试，看着它失败，再写最少代码让它通过。
**使用场景**: 新功能/修 bug/重构前，不要直接写实现代码。
**核心要点**: 铁律："没有先失败测试就不许写生产代码"。先写测试→看它失败→写最小实现→通过→重构。如果你没亲眼看测试失败，就不确定它测对了东西。除一次性原型/生成代码/配置文件外都适用；想"这次跳过 TDD"就是找借口。

#### systematic-debugging
**描述**: 遇到任何 bug/测试失败/异常行为时，禁止先给修复方案——必须先系统性找到根因。
**使用场景**: 用户报 bug、"debug 一下"、东西坏了/抛出异常/变慢了。
**核心要点**: 铁律："不先查根因就不许修"。分四阶段：①建立假设并复现 ②隔离与定位根因 ③验证假设（用最小复现证明）④做修复并回测原场景。症状修复=失败。越紧急越不能乱猜，否则反复返工。

#### using-superpowers
**描述**: 开始任何对话时，先判断是否有技能能匹配当前请求，有就必须先用 skill，再回应用户。
**使用场景**: 任何对话开场/收到任务时。
**核心要点**: 只要感觉"可能有 1% 概率某个技能适用"，就必须先用 skill。把"这是简单问题""我先了解下""我记得这技能"都视为危险信号（找借口），技能门控永远先于回应、先于澄清问题、先于探索。

### 🔗 评审与协作 (3 个技能)

#### requesting-code-review
**描述**: 完成任务、实现较重要功能、或合并前，先自动检查工作是否满足需求，再请求代码评审。
**使用场景**: 代码写完要交差/合并前。
**核心要点**: 不要自己说"完成了"就完事——先自查是否符合需求（功能正确、有测试、无回归），再走评审流程。证据优先于断言。

#### receiving-code-review
**描述**: 收到评审意见时，先理解并核实，不盲从也不敷衍应付，尤其当意见不清晰或值得商榷时。
**使用场景**: 别人给了代码评审反馈，准备照做之前。
**核心要点**: 需要"技术严谨与验证"，不是表演式同意或照单全收。对每条反馈先判断是否合理：合理就执行，不合理的要提出专业反驳，而不是为了避免冲突而盲改。

#### dispatching-parallel-agents
**描述**: 面对 2 个以上彼此独立、无共享状态、无顺序依赖的任务时，把它们并行拆解处理。
**使用场景**: 多个互不依赖的子任务同时出现时提升效率。
**核心要点**: 灵犀适配：把可并行任务清晰拆分为独立子任务，逐个自主完成（替代原版"派发子代理"）。原则——只并行真正独立的任务，有共享状态或顺序依赖的绝不能并行。

### 🏁 收尾与验证 (3 个技能)

#### verification-before-completion
**描述**: 声称"做完了/修好了/通过了"之前，必须先跑验证命令并查看输出，永远先给证据再下结论。
**使用场景**: 正要提交/提 PR/宣称完成之前。
**核心要点**: 铁律："证据优先于断言"。任何"成功/完成/修好"的声明都必须有实际运行验证的输出支撑，不能只凭"我觉得"。提交、合并前必须过验证。

#### finishing-a-development-branch
**描述**: 实现完成、测试全过后，决定如何把工作合入主干时使用。
**使用场景**: 代码写完、测试通过、准备合入时。
**核心要点**: 先确认测试真通过、改动范围清楚，再决定合并/收尾方式；做必要的清理（删临时文件、整理提交），保证主干干净可发布。

#### writing-skills
**描述**: 当我需要创建新技能、编辑现有技能，或验证技能能否生效/可被正确调用时使用。
**使用场景**: 用户要求新增/修改技能，或技能行为异常需要排查时。
**核心要点**: 写 SKILL.md 时 frontmatter 必须包含 `name` 和 `description`；description 说明"何时用"；正文给出清晰步骤/清单；改完要验证技能能被正确发现和调用。

### 🧰 环境与隔离 (1 个技能)

#### using-git-worktrees
**描述**: 开始需要在隔离环境做的功能开发时，先确保有独立工作区（灵犀适配为工作区分支/独立目录，避免污染正在用的环境）。
**使用场景**: 并行开发、实验性改动需要隔离时。
**核心要点**: 灵犀适配：用独立工作区/目录隔离进行中的功能，避免与当前使用环境互相干扰。需要隔离的功能在隔离区完成后，再验证并合入。

## 使用铁律（务必遵守）

1. **开场先查技能**：任何对话/任务开始，先判断是否有技能命中，有就必须用 use_skill 加载对应技能，再回应用户——包括澄清问题之前。
2. **先想清楚再做**：实现前先 brainstorming 澄清需求，别急着写代码；多步任务先 writing-plans。
3. **先测后写**：TDD——先写失败测试再写实现。
4. **先找根因**：debug 前先 systematic-debugging 定位根因，禁止症状修复。
5. **先证明再宣称**：任何"完成/修好"都先跑验证给证据，不许只凭感觉。
6. **规范回应评审**：收到评审意见要技术性核实，不盲从不敷衍。
